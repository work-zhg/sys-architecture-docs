组件版本管理设计

把二方组件版本的决策权从各应用的 pom.xml 上移到平台维护的 BOM， 应用侧一次性改造后永久不动；组件升级通过切换 BOM 版本完成，通过灰度 BOM 控制生效范围。 目标是同时解决组件发布的两个老问题：推广难与全量风险。

1背景与痛点 2核心设计思路 3BOM 怎么产生 4构建怎么用上 BOM

1 · 背景与痛点

公司内部有一批被大量业务应用共用的二方组件（com.xxx:component-c1、c2、c3 …）。 改造前，每个应用在自己的 pom.xml 里直接声明组件版本：

<!-- 应用 A 的 pom.xml：版本硬编码在应用侧 -->
<dependency>
  <groupId>com.xxx</groupId>
  <artifactId>component-c1</artifactId>
  <version>1.0.0</version>
</dependency>

这套模型让"组件发版"和"组件生效"之间隔着 N 个应用团队，衍生出两个结构性痛点。

痛点 1

推广难

组件发了新版本，只有应用主动改 pom.xml、提 MR、走评审、排进版本节奏，新版本才真正落地。 组件方没有任何推动手段，只能逐个群里催。推广成本是 O(应用数 × 组件数 × 升级次数)。

痛点 1 · 后果

版本碎片化

催不动的结果是全站同一组件并存 5~10 个版本。安全补丁无法收口，问题排查要先问"你用的哪版"， 组件方被迫长期维护多分支兼容。

痛点 2

全量风险

反过来，如果用统一 parent 强推版本，一次变更对全部应用的下一次构建立即生效。 组件的一个隐性行为变更就可能同时打穿几十个应用，缺少"先放一部分应用验证"的手段。

痛点 2 · 后果

回退代价高

出问题时无法界定影响面——不知道哪些应用已经构建带上了新版本；回退要逐个应用改回去， 与推广难是同一个问题的两面。

设计目标

组件升级对应用零改动；升级范围可控到应用 / 微环境粒度； 任一制品用了哪些组件版本可追溯、可复现、可回滚；应用侧改造只做一次。

2 · 核心设计思路

2.1 平台维护 BOM，应用只 import

平台产出一个 packaging=pom 的 BOM 制品，集中声明所有二方组件的版本：

<!-- platform-bom:2026.02 —— 由平台生成并上传 Nexus，内容不可变 -->
<project>
  <artifactId>platform-bom</artifactId>
  <version>2026.02</version>
  <packaging>pom</packaging>
  <properties>
    <c1.version>1.0.0</c1.version>
    <c2.version>1.3.0</c2.version>
    <c3.version>2.1.0</c3.version>
  </properties>
  <dependencyManagement>
    <dependencies>
      <dependency><groupId>com.xxx</groupId><artifactId>component-c1</artifactId><version>${c1.version}</version></dependency>
      <dependency><groupId>com.xxx</groupId><artifactId>component-c2</artifactId><version>${c2.version}</version></dependency>
      <dependency><groupId>com.xxx</groupId><artifactId>component-c3</artifactId><version>${c3.version}</version></dependency>
    </dependencies>
  </dependencyManagement>
</project>

2.2 应用侧一次性改造，之后永久不动

应用 A / B / D 的 pom 完全一致，且只改这一次——业务依赖处不再写 <version>：

<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>com.xxx</groupId>
      <artifactId>platform-bom</artifactId>
      <version>${platform-bom.version}</version>  <!-- 来自 parent，默认 2026.02 -->
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>

<!-- 业务依赖不再写版本号 -->
<dependency><groupId>com.xxx</groupId><artifactId>component-c1</artifactId></dependency>

2.3 构建期注入版本，实现零改动升级

版本号是 property，因此流水线可以在构建时覆盖，不动任何代码：

mvn clean package -Dplatform-bom.version=2026.03-RC

这一步是整个设计的支点

组件版本的决策点从"应用代码仓库"搬到了"平台的构建参数"。于是： 推广= 平台改一个参数默认值；灰度= 平台对部分应用传不同的参数值； 回滚= 平台把参数值改回去。三件事都不再需要应用配合。

2.4 为什么一个 BOM 不够：分层 BOM

单个 platform-bom 能解决推广难，但表达不了"只让 A 和 D 先用新版本"。 因此落地时把 BOM 拆成三条并行的版本线，按优先级叠加 import：

层优先级谁来改生效范围
CUSTOM 最高 应用自助申请，生产需 BPM 审批 单个应用
GRAY 中 组件方发起灰度计划 灰度名单内的应用 / 微环境
RELEASE 兜底 组件方正式发布 全局所有应用

三层按 CUSTOM → GRAY → RELEASE 顺序 import。Maven 的 dependencyManagement 对 同一坐标采取先声明者胜出，语义天然就是"优先级高的那层赢"，平台内部的版本合并算法与之保持一致。

3 · BOM 怎么产生

3.1 版本号

BOM 版本号本质上是一个只增不减的批次号，每次变更产生一个新号，永不复用。 落地时在批次号外再带上 BOM 类型与目标环境，便于同一个 Nexus 仓库里区分： Release-10037-prod.RELEASE。 此外每层每个环境都有一个内容为空的默认版本作为兜底，保证应用即使没有任何灰度和自定义， import 也一定能解析到东西。

关键约束：BOM 内容不可变

Nexus release 仓库不可覆盖，Maven 本地仓库又会缓存。若允许同一个版本号改内容， 就会出现"同一制品号在不同机器上构建出不同依赖"的幽灵问题。 所以任何变更——包括回滚——都只能产生新版本号，绝不修改已发布的 BOM。

3.2 三层 BOM 分别怎么写

层触发写入内容
RELEASE 组件发布单审批通过后执行发布 全量：复制上一版本的完整清单，再覆盖本次变更的组件
GRAY 组件方发起灰度计划 增量：只写本次灰度涉及的组件，同时登记灰度范围（应用名单 / 微环境 / 全量）
CUSTOM 应用提交申请，生产环境走审批 增量：只写该应用指定的组件版本

为什么 RELEASE 必须全量、其余可以增量：RELEASE 是优先级最低的兜底层， 没有下一层为它补齐缺失的组件，必须自包含；GRAY / CUSTOM 在它之上做覆盖，只需写差异。 全量的代价是内容随发布次数线性增长，收益是任一历史版本都能直接 import、可精确回到任意时间点。

灰度 BOM 的合并

一个应用可能同时命中多个灰度计划（计划 P1 灰度 c1、P2 灰度 c2，而该应用两个名单都在）， 但 Maven 只能 import 一个 GRAY BOM。平台的做法是：按应用求出它命中的灰度集合， 以这个集合本身作为幂等键去查已有的合并记录——命中就直接复用，没命中才生成一个新的合并 BOM； 集合里只有一个灰度时直接复用原 BOM，不产生新版本。 因此合并 BOM 的数量取决于"有多少种不同的命中组合"，而不是应用数量。

回滚

回滚不是删掉新版本或重新上传旧版本，而是用旧的组件版本再发布一次： 读取发布前记录的线上版本，走与正式发布完全相同的路径，产出一个号更大、内容等于旧状态的新 BOM。 这样版本号保持单调递增，不违反不可变约束，同时留下完整的审计痕迹。

注意：回滚只影响之后的构建，不追溯已构建出的制品； 线上回退仍需部署回滚到旧制品——旧制品的依赖在构建时已固化，天然正确。

3.3 从平台数据到 Nexus

BOM 的权威副本在平台内，Nexus 上的 pom 文件只是给 Maven 消费的物化产物。写入分两步： 先在事务内落地 BOM 的版本与内容并标记为"待上传"，再在事务外生成 pom XML 上传 Nexus，成功后标记为"已上传"。

上传失败不阻塞主流程：定时任务会扫描"待上传"的记录做补偿重试，构建期读取 BOM 时也会再触发一次作为兜底； 同一版本的并发上传由分布式锁收敛，保证只上传一次。

4 · 构建怎么用上 BOM

这一节是"版本怎么真正作用到制品上"。链路分四步： 构建前解析并固化 → 注入参数构建 → 构建后依赖校验 → 制品入库。 其中第三步是整套设计能否成立的关键——没有它，BOM 只是一个建议，而不是约束。

4.1 构建前：解析并固化

流水线在拉代码之后、执行 Maven 之前先问平台一次："这个应用、这个环境、这个制品号， 本次该用哪几个 BOM 版本？"平台一次性完成两件事：算出三层 BOM 的版本号， 并把结果与制品号绑定存下来。

解析时有三个输入会影响结果：是否指定了微环境（决定走微环境灰度还是主环境灰度）、 是否要求忽略灰度（想要一个不含任何灰度组件的干净制品）、是否强制重算。

幂等性来自固化，而不是来自"当前状态"

同一制品号重新构建，默认读回首次固化的版本号，而不是重新按"当前最新"解析。 否则组件在两次构建之间发了新版本，同一个制品号就会产出不同内容——这会让回滚与问题复现彻底失去意义。 只有显式要求强制重算时，才允许按当前状态重新解析。

4.2 构建中：注入参数

解析结果以 property 形式注入，应用 pom 与 parent 都不需要知道具体版本值：

mvn clean package -Dplatform-bom.version=Release-10037-prod.RELEASE
# 分层落地时是三个同样形式的参数，分别对应 CUSTOM / GRAY / RELEASE

三层 import 的顺序写死在 parent 里，应用只继承、不参与。 顺序写错会让灰度和自定义静默失效，所以它必须是 parent 的一部分，而不是应用可改的内容。

4.3 构建后：依赖一致性校验

为什么必须有这一步

Maven 的 dependencyManagement 只对未显式声明版本的依赖生效。 只要应用侧任何一处写了版本号，BOM 就会被静默覆盖——不报错、不警告、构建照常成功。 也就是说，改造完成的应用随时可能被一次不起眼的 MR 悄悄改回去，而平台完全无感。 没有校验，第 1 节的"推广难"会以一种更隐蔽的形式回归。

BOM 被静默绕过的几种方式

方式表现会报错吗
直接写版本号依赖处补回 <version>1.0.0</version>否
自建 property用自己的 property 绕开 BOM 的命名否
本地声明抢先在 import BOM 之前声明同坐标，先声明者胜出否
传递依赖带入第三方库传递引入了组件旧版本否
排除后手动引入exclusions 排除后自行声明，脱离管控否
多模块局部覆盖子模块自己声明版本，与整体口径不一致否

这几种方式的共同点：构建全部成功。所以校验不能依赖 Maven 自身报错， 必须由平台在构建之后主动比对。

怎么采集"实际用了什么"

在同一次 Maven 调用里顺带导出依赖清单，而不是另起一次构建——否则参数或 profile 一漂移， 校验的就不是制品那份依赖树了。清单要包含传递依赖（传递引入的旧版本恰恰最难发现）， 并以最终产出可部署制品的模块为准。

怎么算"应该用什么"

平台按固化结果（而不是当前最新）还原期望清单：取该制品固化的三个 BOM 版本， 展开各自内容后按 CUSTOM > GRAY > RELEASE 优先级合并，得到"组件 → 期望版本"的映射。 这与 Maven 侧的 import 顺序语义严格对齐，两边算出来的必须是同一个答案。

比对结果分四类

结果含义常见原因
一致实际版本 = 期望版本—
版本不符组件在 BOM 中，实际解析出别的版本pom 硬编码、本地声明抢先、子模块覆盖
未纳管依赖了公司域内组件，但不在任何 BOM 中组件未接入、新增子模块漏登记、第三方传递带入
未使用BOM 中有，制品实际没依赖正常：BOM 是全量清单，应用只用其中一部分，不告警

不一致怎么处置

环境版本不符未纳管理由
dev告警告警开发期频繁试错，硬阻断影响效率
sit中断告警问题必须在测试环境暴露，不能带到生产
pre / prod中断中断生产制品的依赖必须 100% 可解释

校验失败的正解不是加白名单

如果应用确实需要一个与 BOM 不同的版本，正确做法是走 CUSTOM 层申请（生产需审批）， 让这个差异在平台内可见、可审计、可撤销；而不是在 pom 里硬编码再申请豁免。 白名单只留给"组件尚未接入纳管"这类过渡场景，且必须带有效期，到期自动失效并重新阻断。

中断点与失败信息

中断点设在制品入库之前：构建步骤返回失败，制品不写入制品库、不产生可部署版本。 失败信息必须直接可操作——只说一句"校验不通过"等于把排查成本推给应用方，应当包含三样东西： 期望值来自哪一层 BOM（否则应用方判断不了是不是灰度导致的）、 实际值由哪行 pom 或哪条传递路径引入、本次构建固化的 BOM 版本。

[依赖校验] 未通过：2 项不一致，构建已中断

com.xxx:component-c1   期望 1.1.0（来自 GRAY 灰度计划 #51）   实际 1.0.0
  └─ 来源：app-service/pom.xml:88 显式声明了 version
  └─ 处理：删除该 version；若确需固定版本，请提交 CUSTOM 版本申请

com.xxx:component-c9   未纳管                                 实际 0.8.2
  └─ 来源：由 com.third:sdk:2.1.0 传递引入
  └─ 处理：联系组件 Owner 接入 BOM 纳管，或在应用侧 exclude

为什么门禁放平台侧，而不是 parent 插件里

技术上也可以用 maven-enforcer-plugin 自定义规则在构建早期失败，反馈更快。 但把门禁只放在 parent 里有个致命问题：规则更新本身又变成一次推广—— 改规则要发新 parent，发了新 parent 还要等各应用升级，正好踩回第 1 节的痛点，而且应用可以跳过插件。

所以：平台侧后置校验是唯一门禁（规则随时可调、无法绕过、有全局视图）， enforcer 规则只作为可选的本地快速反馈，让开发者在本地提前发现问题，但不作为准入依据。

4.4 构建后：记录下来

校验通过后，除了制品入库，平台还要把"这次构建到底用了什么"记下来： 固化的三层 BOM 版本（并标注是否用了灰度或自定义，制品列表上可以直接看到"含灰度组件"）、 校验结论、以及实际依赖清单（每个组件的实际版本与引入路径）。

这份记录的真正价值

它让"某个组件版本现在被哪些线上制品实际使用"从一个需要全量扫代码才能回答的问题， 变成一次查询。安全漏洞应急、组件下线评估、灰度覆盖率统计都依赖这份数据—— 这是校验环节除门禁之外的第二重收益。

补充：除了构建后校验，平台还可以在 MR 阶段静态扫描应用 pom 里有没有硬编码版本。 两者是互补的——静态扫描看的是源码意图，能提前拦截但看不到传递依赖； 构建后校验看的是依赖树事实，能发现全部问题但只能在构建时拦截。
