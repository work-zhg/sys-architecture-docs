微环境设计

微环境用来解决同一套测试环境上多个需求并行测试的问题。 思路是：不为每个需求复制一整套环境，而是只为被改动的应用建立隔离副本， 其余应用继续复用主环境，再用请求打标把不同需求的流量分别引到各自的副本上。

1 · 背景：并行测试的冲突

典型场景：应用 A 上同时有两个需求在开发，feature1 和 feature2，都要进测试环境验证。 但测试环境（SIT）只有一套，A 只有一份部署。

现状 1

排队等待

feature1 先上测试环境，feature2 只能等。需求越多排队越长，测试环境成了交付流程里最堵的一段。

现状 2

互相覆盖

两个分支轮流往同一个环境上部署，谁后部署谁生效。测出来的问题经常分不清是自己的改动还是别人的。

现状 3

复制整套环境太贵

最直接的办法是给每个需求拉一整套环境，但几十上百个应用全量复制一遍， 机器成本和维护成本都无法接受，而且绝大多数应用在这个需求里根本没有改动。

微环境的思路

一个需求真正改动的通常只有 1~3 个应用。那就只为这几个应用建副本： feature1 建微环境 1，里面只部署改过的 A；feature2 建微环境 2，里面只部署改过的 A。 两个副本各自独立，其余应用共用主环境。 再给请求打上微环境标签，让 feature1 的流量走微环境 1 的 A，feature2 的流量走微环境 2 的 A。

由此微环境要解决三个隔离问题，分别对应本文的三节：

隔离要解决什么手段
CI 隔离微环境构建出的包不能污染主环境，但又要能依赖主环境的包Nexus 独立仓库 + 代理主环境仓库
CD 隔离微环境的实例不能和主环境、其他微环境抢资源或互相干扰每个微环境一个独立 namespace
流量隔离不同需求的请求要能分别落到各自的副本上请求打标 + 同标优先 + 回落主环境

2 · 整体模型

微环境不是一套完整环境，而是"主环境 + 若干差异副本"。 它依附于某个主环境（dev 或 sit），自己只持有被改动的那几个应用。

一个微环境由平台统一分配标识（形如 subenv + 随机串），这个标识会同时用作三件事：

  • Nexus 上那一组仓库的名字后缀 —— CI 隔离
  • K8s 上那个 namespace 的名字 —— CD 隔离
  • 请求上打的那个标签的值 —— 流量隔离

三层隔离共用同一个标识，是整套设计能串起来的前提： 构建产物、运行实例、请求流量都用同一个名字对齐，不需要额外的映射关系。

3 · CI 隔离：Nexus 仓库分层

3.1 要解决的矛盾

微环境里的应用 A 改了代码，构建会产出新的 jar。这里有一对矛盾：

  • 不能往主环境仓库传：否则主环境和其他微环境构建时会拉到这个还没验证的包，污染面失控
  • 又必须能拿到主环境的包：A 依赖 B、C 和一堆二方三方库，这些包都在主环境仓库里，不可能为每个微环境复制一份

3.2 做法：独立 hosted + group 代理主环境

创建微环境时，平台在 Nexus 上为它建一组仓库：

  • 两个 hosted 库：一个放 release 版本、一个放 snapshot 版本，只有这个微环境的构建往里传包
  • 一个 raw hosted 库：放非 Maven 类的制品
  • 一个 group 库：成员是"本微环境的两个 hosted 库"+"主环境的 group 库"

3.3 为什么这样就够了

关键在于 group 的查找顺序：先查自己的 hosted 库，查不到再穿透到主环境。于是：

取哪个包结果
A 自己刚构建出的包命中微环境 hosted 库，拿到本微环境的版本
B、C 等没改动的应用的包微环境库里没有，穿透到主环境，拿到主环境的版本
二方组件、三方开源库同上，穿透到主环境

这正是"隔离但不重复"的效果：写入是隔离的（只往自己的 hosted 库传）， 读取是叠加的（自己没有就用主环境的）。微环境不需要复制任何一个主环境的包。

方向性是关键

代理关系是单向的：微环境 group 代理主环境 group，反之绝不成立。 主环境永远看不到微环境的包——这保证了微环境里再怎么折腾，都不可能影响主环境和其他微环境的构建。

4 · CD 隔离：独立 namespace

4.1 做法

创建微环境时，平台在对应集群上建一个以微环境标识命名的 K8s namespace， 这个微环境里部署的所有应用都进这个 namespace。

对象主环境微环境
namespace主环境自己的 namespacesubenv1（就是微环境标识）
DeploymentAA-subenv1（名字带微环境后缀，便于识别）
部署目标集群 + 主环境 namespace集群 + 微环境 namespace

namespace 带来的是 K8s 原生的隔离能力：名称空间独立、资源配额独立、 网络策略和服务发现的边界清晰，删除时一次性回收干净，不会有残留资源。

4.2 只部署改动的应用

微环境创建出来是空的，需要显式把应用"绑定"进来，绑定之后该应用才会在这个微环境里有一份部署。 没绑定的应用在这个微环境里就是不存在的——请求到了这里会回落主环境（见第 5 节）。

这是微环境成本低的根本原因：绑定几个应用就只花几个应用的资源， 而不是复制整套环境。

4.3 资源回收

测试环境的资源是稀缺的，微环境又容易建完就忘，所以回收要做成默认行为：

动作效果适用
禁用把微环境里所有 Deployment 的副本数调成 0，保留配置 暂时不用，但还想留着，随时能启用恢复
启用副本数恢复，实例重新拉起继续测试
删除删 namespace + 删 Nexus 那组仓库，资源全部释放需求测完，微环境不再需要
过期回收微环境带有效期，定时任务到期前通知负责人，到期后自动清理 兜底，防止无人认领的微环境长期占资源

"禁用"这一档很重要：并行测试常常是断断续续的， 如果只有删除一个选项，用户就会倾向于一直留着不删。副本数调 0 让"留着"几乎不花钱。

5 · 流量隔离：请求打标与回落

前两节解决了"副本怎么建出来"，这一节解决"请求怎么找到正确的副本"。 整个机制只有三条规则：打标 → 透传 → 同标优先、无则回落。

5.1 打标：把人和微环境绑定

标从哪来？做法是把测试人员绑定到微环境上：微环境创建时登记一批用户标识， 这份绑定关系同步给网关。请求进来时，网关识别出是哪个用户，就给这个请求打上对应的微环境标签。

这样选择对测试人员是无感的——不需要改客户端、不需要手工加 header、不需要记住自己该走哪个环境， 用自己的账号登录，流量自然就进了自己的微环境。

5.2 透传：标要跟着整条调用链走

标打在入口还不够，它必须随着调用链一路传下去：A 调 B、B 调 C 时，标都要还在。 这一步依托调用链上下文透传（和 traceId 同一套机制），业务代码无需感知。

"回落"是整套设计成立的关键

正因为找不到就回落主环境，微环境才可以只部署改动的应用。 如果没有回落，每个微环境都必须部署全套应用才能跑通链路——那就退化成"复制整套环境"， 成本问题原封不动地回来了。

5.4 打标只影响选址

标签的作用范围仅限于服务发现选实例这一层，不进入业务逻辑，也不改变请求内容。 应用代码里没有任何一处需要判断"我现在在哪个微环境"—— 这让微环境对业务代码完全透明，应用不需要为支持微环境做任何改造。

6 · 完整流程

微环境的生命周期分三段：一次性准备、日常循环、用完回收。

7 · 边界与注意事项

定位

微环境 ≠ 灰度发布

两者都用"打标 + 按标路由"，但目的不同：微环境解决测试环境并行占用， 按人分流，生命周期以需求为单位；灰度发布解决生产变更风险，按业务规则分流。 不要把微环境的机制直接搬到生产上用。

限制

数据层通常不隔离

微环境隔离的是构建产物、运行实例和流量，数据库、缓存、消息队列一般仍共用主环境。 因此两个微环境同时改了同一张表的结构，或者消费同一个 topic，还是会互相干扰。 涉及存储变更的需求要特别留意。

限制

标断了就回不来

调用链上任何一处没有透传标（比如经过了不支持透传的中间件、异步任务、 定时任务发起的调用），后续链路就会全程走主环境。 排查"我的改动怎么没生效"时，这是第一个要查的点。

限制

依赖主环境的健康

微环境大部分链路都落在主环境上，主环境不可用时微环境也测不了。 微环境降低的是并行成本，不提供额外的可用性。
