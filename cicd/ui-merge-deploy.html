UI 合并部署设计

UI 应用的产物就是一堆静态文件，不需要为每个应用单独跑一组容器。 做法是：Pod 挂载 NAS，部署时把 UI 资源解压到 NAS 上的版本目录， 再用切换软链的方式让新版本生效——一次切换，整个站点原子地从旧版本换到新版本。

1 · 背景：两个问题

UI 应用按常规的容器化方式部署，是把前端构建产物打进镜像，每个应用跑一组自己的 Nginx Pod。 这套做法用在 UI 上有两个问题。

问题 1

资源与发布效率

几十个 UI 应用就是几十组 Pod，每组都在跑一个几乎一样的 Nginx， 真正的差异只是几十兆静态文件。发一个版本要走"构建镜像 → 推仓库 → 拉镜像 → 滚动重启"， 改一行文案也得几分钟，而且每次都在重启一个本来不需要重启的进程。

问题 2

更新过程的一致性

如果改成直接往共享目录里覆盖文件，就会出现新旧混用： 浏览器刚拿到新的 index.html，按里面的引用去请求 app.a1b2c3.js， 而这个文件还没复制完——直接 404 白屏。反过来先传 js 后传 html 也有对称的问题。

第一个问题指向"不要把静态资源放进镜像"，第二个问题指向"版本切换必须是原子的"。 这两点合起来就是本文的设计。

2 · 核心设计

2.1 存储与计算分离

Nginx Pod 里不放任何 UI 资源，只挂载一块 NAS，站点根目录指向 NAS 上的部署目录。 于是 Pod 变成了纯粹的、无状态的、可以长期不动的静态文件服务器：

镜像部署NAS 软链部署
资源在哪打进镜像层NAS 上的版本目录
发版动作构建镜像 → 推送 → 拉取 → 滚动重启上传解压 → 切软链
Pod 是否变动每次重建完全不动
耗时量级分钟秒
多副本一致性滚动期间新旧副本并存共享同一份 NAS，天然一致

2.2 两类目录：版本目录与部署目录

NAS 上的目录分成职责完全不同的两类，这是整套设计的骨架：

目录职责特点
版本目录 按"应用 + 版本号"存放解压后的静态资源 只增不改。一个版本解压进去之后内容永不变动，多个历史版本并存
部署目录 Nginx 站点根目录，里面只有软链，不存实际文件 每个应用一个软链，指向该应用当前生效的那个版本目录
 
# 版本目录：写入一次，永不改动
/nas/{环境}/app-a/2024/app-a/    index.html  app.a1b2c3.js  …
/nas/{环境}/app-a/2025/app-a/    index.html  app.d4e5f6.js  …
/nas/{环境}/app-b/318/app-b/     …

# 部署目录：Nginx 的站点根目录，全是软链
/nas/{环境}/{集群}/{服务组}/
    app-a  ->  /nas/{环境}/app-a/2025/app-a     ← 当前生效版本
    app-b  ->  /nas/{环境}/app-b/318/app-b

版本目录不可变是这套设计的前提：因为它不会被改动， 软链指向它就永远安全——不存在"正在被服务的目录同时在被覆盖"这种情况。

2.3 部署就是两步

把新版本资源准备好，再把软链指过去。前一步慢但不影响线上，后一步快且瞬间生效：

幂等设计：解压前先判断该版本的制品是否已存在，存在就整步跳过。 这样同一个版本重复部署（重试、回滚回来）不会重复解压，也不会出现"正在解压的半成品被软链指到"的情况。

3 · 为什么必须用软链

这是整套设计里最容易被质疑的一点：既然都挂 NAS 了，为什么不直接把新文件覆盖进部署目录？ 答案是一致性——前端资源是一组必须整体生效的文件。

3.1 逐文件覆盖必然出现不一致窗口

现代前端构建产物里，index.html 引用的 js / css 文件名都带内容哈希：

旧版本  index.html  →  引用  app.a1b2c3.js
新版本  index.html  →  引用  app.d4e5f6.js

逐个文件覆盖时，复制是有先后顺序的，中间必然存在一段"html 和 js 不是同一个版本"的时间：

3.2 软链把"多次修改"变成"一次修改"

关键在于修改的对象变了：

修改对象修改次数中间状态
逐文件覆盖成百上千个文件成百上千次存在，且持续秒级
软链切换一个符号链接一次不存在可观察的混用状态

本质：把版本切换收敛成单点

静态资源天然是"一组文件必须同版本"的整体。逐文件覆盖是把整体拆成了很多次独立变更， 每次变更之间都可能被请求观察到。软链的作用是把这个整体重新收拢成一个指针—— 指针要么指向旧版本，要么指向新版本，没有第三种状态。

3.3 附带的好处

  • 回滚极快：旧版本目录还在，把软链指回去就行，和发布是同一个动作
  • 发布可预检：新版本目录已经落地但尚未生效，需要的话可以先校验完整性再切
  • 多副本一致：所有 Pod 共享同一份 NAS，切链对全部副本同时生效，不存在滚动期间的版本参差

4 · 合并：一组 Pod 承载多个 UI

因为 Pod 里不含任何应用资源，一个 Nginx Pod 服务哪些应用， 就只取决于它挂载的部署目录下有哪些软链。于是"合并部署"自然成立： 多个 UI 应用共用同一组 Pod，各自在部署目录里占一个软链，按路径区分。

4.1 合并带来的收益

收益

资源收敛

几十组 Nginx Pod 收敛成一组。Pod 数量不再随 UI 应用数量线性增长，新增一个 UI 应用的边际成本接近零。

收益

发布互不干扰

虽然共用 Pod，但每个应用只动自己那个软链。A 发布不会让 B 重启， 也不会因为 A 的问题牵连 B——因为根本没有重启这个动作。

收益

天然适配微环境

微环境里 UI 的改动同样只是"多一份资源"。用一组固定的 Pod， 在部署目录下按微环境再分一层目录，每个微环境一套自己的软链，就实现了 UI 的微环境隔离， 不需要为每个微环境新建 Nginx。

6 · 注意事项

替换指向目录的软链，必须显式禁止跟随

这是实现上最容易踩的坑：当部署目录下已经存在一个指向目录的同名软链时， 普通的"强制创建软链"会跟随旧软链进入它指向的目录， 在旧版本目录里面再建一个链接，而不是替换原来那个。 表现为发布"成功"但页面还是旧的，且版本目录里凭空多出嵌套链接。 创建软链时必须带上不跟随符号链接的选项。

切换本身要做成原子替换

"删掉旧链接再建新链接"是两步操作，中间有一个极短的窗口链接不存在，此时请求会 404。 更稳的做法是先创建一个临时名字的新链接，再用原子改名覆盖旧链接， 让切换过程始终有一个有效链接存在。 窗口虽然只有微秒级，但高流量站点仍可能采到——既然可以彻底消除，就不要留。

事项说明
上传的完整性 制品先以临时名上传、完整后再改名，避免半个包被当成正式制品解压
版本目录清理 版本目录只增不减，必须有清理策略；清理时要排除当前生效版本与近期可回滚版本
浏览器缓存 html 必须禁缓存、带哈希的静态资源可长缓存。否则服务端切完了， 用户浏览器里还是旧 html 指向旧 js——不一致从服务端转移到了客户端
NAS 成为关键依赖 所有 UI 的可用性都压在这块存储上。NAS 抖动会同时影响全部合并在一起的应用， 需要相应的容量与可用性保障，必要时按业务重要性拆分多块
合并的影响面 共用 Pod 意味着共用 Nginx 配置与资源配额。 单个应用的异常流量会影响同组其他应用，重要应用可以单独成组
不适用的场景 不挂 NAS 的集群、或需要 CDN 分发的 C 端站点，走各自的部署方式 （如资源直接同步到对象存储 + CDN），与本方案并行存在
